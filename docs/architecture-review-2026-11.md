## 1. 项目全景

### 1.1 实际定位（与 README 的偏差）

README 仍写「第一阶段：核心引擎 + 五类节点 + 三个范例」，与代码严重脱节：

| 维度 | README 描述 | 代码实际 |
| --- | --- | --- |
| 阶段 | 第一阶段 | 已到 phase5（偏差修正 G1~G8） |
| 节点类型 | 5 类 | 14 个枚举成员（`domain/models/enums.py:34-57`） |
| 范例 | 3 个 | 12 套 / 15 个 YAML |
| 能力面 | 画布 + 引擎 | + 治理（RBAC/租户/审计/计量/计费/调度）、生态（沙箱/插件 SDK/市场/SSO/连接器/评估/发现）、NL 编排、上下文引擎 |
| 版本 | - | `pyproject.toml` 仍是 0.1.0，CHANGELOG 到 1.4.0 |

真实定位应表述为：**YAML 声明式 + 画布双模编辑、单机可跑、面向私有化的多 Agent 工作流编排与治理平台**。能力面已覆盖「编排—执行—治理—生态」四层，但多数治理/生态能力停在「可演示、未接线」。

### 1.3 关键依赖关系（真实调用方向）

1. **引擎只认 Protocol**：`engine/abstractions/` 定义 `IWorkflowEngine`，`engine/adapter/langgraph_adapter.py` 是全仓唯一 `import langgraph` 的位置——但文件头自述「验证期桩」，实际执行走自研 `Scheduler`，也就是说 LangGraph 依赖目前是**净负担**（装而不用）。
2. **节点执行器注册表**：`engine/node_executor_registry.py` 以 `dict[NodeType]` 注册；`register_phase2_executors` / `register_supervisor_executor` 全仓零调用 → SUPERVISOR/PLUGIN 节点执行即「执行器未注册」。
3. **前端单向依赖**：`App.tsx` 持有唯一状态 → props 下发；无 store、无路由；`AdminConsole` 用 switch 渲染 18 个面板，面板各自直连 API 客户端。
4. **治理是旁路**：`governance_factory.create_governance_chain()` 只装配 auth/tenant/quota 三个拦截器，审计、计量、预算、全局调度拦截器**从未实例化**。

## 2. 核心功能模块与成熟度

### 2.1 执行链路（端到端）

`YAML → YamlWorkflowParser（语法/版本/五要素/pydantic 判别联合）→ GraphTopologyValidator（拓扑）→ NodeConfigurationValidator（配置）→ GraphCompiler（Kahn 拓扑 + 条件边元数据）→ Scheduler（单游标循环）→ NodeExecutor（12 类）→ event_callback（SSE/事件）→ 前端实时着色`

链路本身设计清晰，问题集中在**语义完备性**，而非分层。

### 2.3 前端结构

- **画布**（29.6k 行 / 55 文件）：React Flow + 12 类节点视图 + 配置面板（`NodeConfigurationPanel.tsx` **3710 行**）+ 撤销栈（自研，50 步）+ 视口持久化。
- **管理后台**：18 个面板 4 组（画布与编排 / 安全与合规 / 生态与扩展 / 评估与发现），全部首屏同步加载。
- **工程化短板**：无路由/无 URL 深链；无状态容器（props drilling）；无 CSS 体系（145 处内联 + 105 处 `<style>` 注入，`darkTokens` 引用 1153 次）；15 个 API 客户端各自重写 token/响应处理，异常类 3 份；零 `import()` 代码分割；无 e2e。

### 2.4 测试现状

| 套件 | 规模 | 特点 |
| --- | --- | --- |
| 后端 unit | 97 文件 / 2097 例 | 分布失衡：VKB 与 run_log 占 20+ 文件，引擎并发/挂起几乎无覆盖 |

**门槛现状**：无 CI（仓库无 `.github/`、无 Dockerfile/compose）；无覆盖率阈值；`docs/tech-debt-ledger.md:23` 记录的历史基线是「26 个失败被接受」，但本次实跑为 0 失败——台账已过期，恰好说明「没有人在持续跑测试」。

## 3. 总体判断（v2 修订）

**优势（应当守住）**
1. 领域模型与校验链扎实（YAML v1.0/1.1/1.2 兼容、判别联合、拓扑校验），是可对外承诺的**契约资产**——这是全项目唯一具备差异化潜力的东西。
2. 引擎与框架解耦（Protocol + 适配层），换执行内核不动业务；同时意味着「契约可移植」是可验证的，不是口号。
3. 治理能力「面」铺得全，降级矩阵思路正确（默认安全、显式开启、优雅降级），且是**架构内建**而非商业版补丁。
4. 数据侧纵深：14 类节点里有 `data_source` + `data_transform`（21 个算子），这是 Dify 结构上不做的方向。
5. 前端画布交互成熟，回归测试密度高（916 例）；后端 2797 例 exit 0。

**风险（应当先止血）**
1. **安全**：API 无有效鉴权（令牌可伪造、默认密钥、SSO 不验签、代码节点 `exec`），不具备对外暴露条件。
2. **正确性**：并发/挂起/续跑三处语义缺失，却已有对应 API 与 UI，形成「看似支持、实则不生效」的认知陷阱。
3. **可信度**：审计查询恒空、评估为桩、发现用伪向量——治理面板展示空数据，损害平台信任。
4. **工程化**：无 CI、无容器化、无部署文档；前端 3710 行单文件；API 客户端重复。
5. **文档漂移**：README 停在第一阶段；`phase4_ecosystem_summary.md` 声称默认启用但 `settings.py` 默认全 False；引用不存在的 `config/phase4.yaml`。

**战略判断（v2 新增）**

v1 的排序原则是「按缺什么补什么」，这在没有定位的情况下是对的，但它会导致一个隐性问题：
**每个方向单独看都合理，合起来却没有一个能对外讲清楚「为什么选你」。**

对标 Dify 1.19 / n8n / LangGraph / Temporal 之后（详见 `docs/differentiation-strategy-2026-11.md`），
可赢的位置只有三条，且都是竞品**结构上不能站**的位置：

1. **可嵌入（OEM/白标）**——Dify 许可证禁止多租户对外服务与去 logo，ISV/行业 SaaS 是真空。
2. **声明式契约（YAML 即接口）**——Dify 的 DSL 是导出物，不是可校验规范；这是唯一能对开发者讲清的差异。
3. **数据 × AI 混合 DAG**——Dify 不做 ETL，Airflow 不懂 LLM。

**因此 v2 的排序规则改为「路线驱动」，用三层筛子**：

| 筛子 | 含义 | 处置 |
| --- | --- | --- |
| ① 路线必需 | 不做则 R1/R2/R4 任一路线不成立 | 立即排期 |
| ② 通用正确性 | 阻塞所有路线（安全、CI、接线） | 视为「入场券」，不属任何路线但必须先做 |
| ③ 锦上添花 | 不服务任何路线，或 ROI 不确定 | **冻结 6 个月**，不再新增面板 |

这条规则的价值在于：它把「该不该做」从审美争论变成一句可执行的话——
**这个功能服务哪条路线？答不上来就不做。**

## 4. 优先级校准：哪些方向被升级、降级、删除

下表是 v1 → v2 的处置变更，逐条给出理由。**这是本文档最需要评审的部分**，因为它直接决定未来 6 周不再做什么。

| 原方向 | v1 优先级 | v2 处置 | 理由 |
| --- | --- | --- | --- |
| 多租户 SQL 强制隔离 | 安全项 P0 | **升级：R1 商业前提** | 不再是安全补丁，而是产品形态。白标交付的第一句问话就是「能不能隔离」 |
| 租户配额 + 计量落盘 | P0（治理可信） | **升级：R1 交付门槛** | 客户拿去做多租户售卖，没有配额就无法二次定价 |
| 事件出口（Webhook/SSE） | P2（生态） | **升级：R1 接口契约** | 嵌入方要订阅执行事件，属 SDK 契约，不是可选集成 |
| 无状态水平扩展 | 未列 | **新增 P1** | 可嵌入 = 多副本部署；执行状态全落库是前提 |
| OEM 构建（去 logo / 可主题化） | 未列 | **新增 P1（2 人日）** | 白标最低要求，前端已有主题令牌，成本极低、收益极高 |
| `wfp` CLI | P2「开发者生态」 | **升级：R4 入口，P0** | 复用率最高的资产，是获客漏斗顶部而非附加品 |
| 并行扇出 + 汇聚 | P1「多 Agent 模式」 | **保持 P1，理由改写** | 从「Agent 模式」改为「R2 数据管道的吞吐前提」，避免为并行而并行 |
| 流式 / 大批量处理 | 性能项 | **升级：R2 必需 P1** | 当前全内存，10 万行即 OOM，ETL 场景不成立 |
| LangGraph 适配 | 「建议先删依赖」 | **反转：保留并补齐** | 「同一份 YAML 在两种运行时等价」是对 Dify 的硬差异证明，删了就失去可移植性叙事 |
| 模板市场 / 插件市场 | 未列 | **明确删除** | 网络效应已被 Dify 锁定，冷启动不可能 |
| 表单化输入 | P2 | **冻结** | 服务「业务人员自助」，但 R1 客户是自己的产品团队，不需要 |
| NL→工作流 Copilot | P2「差异化卖点」 | **冻结** | 竞品同类功能已商品化；且与本项目的「确定性契约」叙事相冲突（生成物不可控） |
| Agent 能力发现（真 embedding） | P2 | **降级为技术债清理** | 只保留「伪向量换真向量」这一项，删掉「推荐面板」 |
| 评估闭环 | P2 | **冻结** | 需要真实用户与场景集才有价值，当前没有 |
| 自研向量库 / 模型聚合面板 / Prompt IDE | 未列 | **不进入路线** | 商品化能力，做了不加分 |

## 5. 方向一：功能拓展（按路线重排）

### 5.1 层 0：入场券（2 周，阻塞所有路线）

不服务任何单一路线，但**不做则三条路线全部讲不出口**。

| # | 能力 | 实现思路 | 收益 | 成本 |
| --- | --- | --- | --- | --- |
| F1 | 检查点接线 + 断点续跑 | `Scheduler` 构造传入 `checkpoint_repository`；`recover_instance` 从最近 checkpoint 的 `next_node_id` 续跑；PG 补 `(instance_id, round_index)` 唯一约束 | 崩溃可恢复；「可回放」叙事的物理基础 | 5 人日 |
| F2 | 全局步数/预算护栏 | 增 `max_steps`（默认 500）与 token/成本预算，超限抛 `WF_BUDGET_EXCEEDED`；与 loop 计数解耦 | 杜绝无限环烧钱 | 2 人日 |
| F3 | 人工审核挂起（HITL） | 消费 `control_flow` 的 `suspend`：落 checkpoint + 实例置 `WAITING_REVIEW`；`/review` 路由唤醒 | 审批类场景从「假支持」变真支持 | 6 人日 |
| F4 | 回滚/重放真实现 | 路由改调 `RollbackReplayService`；区分 `strict_replay`（复用记录输出）与 `re_execute`（真跑） | 「可审计」不能只是日志，得能重放 | 6 人日 |
| F5 | CI + 容器化 | GitHub Actions（`ruff + pytest -q` / `tsc + vitest`）+ 多阶段 Dockerfile + compose | 从「仓库」变「产品」 | 5 人日 |

> 小计 24 人日。**这一层做不完，后面三层都不要开始**——否则又是在 PPT 上加一层。

### 5.2 层 1：R1 内核化（可嵌入 / 白标，增量 37 人日）

目标是让引擎能被第三方产品嵌进去卖。检查标准只有一条：**外部 Demo SaaS 跑通 3 个租户、配额生效、审计可导出**。

| # | 能力 | 实现思路 | 收益 | 成本 |
| --- | --- | --- | --- | --- |
| F6 | 多租户强隔离 | 仓储基类强制注入 `tenant_id`；PG 启用 RLS 双保险；跨租户访问在 DAO 层抛错而非靠中间件 | 白标交付的前提 | 6 人日 |
| F7 | 租户配额 + 计量落盘 | 补 `usage_record / budget / tenant_quota` 三表；拦截器链在执行前后记账；超配额返回 `429 + 配额详情` | 客户可二次定价 | 8 人日 |

## 6. 方向二：技术改进（按路线重排）

### 6.1 安全红线（P0，本周启动；其中两项已升级为商业前提）

| 项 | 现状 | 建议 | 成本 | 归属 |
| --- | --- | --- | --- | --- |

| 代码节点 | `exec()` 于线程内，超时不可杀（`code_execution/runner.py:169`） | 默认走子进程 + 资源限额；`exec` 仅测试环境 | 2 人日 | 入场券 |

| SSO | 断言不验签（`saml_adapter.py:76`） | `python3-saml` / `authlib` 真验签 + 有效期/受众校验 | 5 人日 | 冻结至有客户提出 |

### 6.2 架构（三处判断变更）

1. **事件总线：从「可选项」升为「R1 的地基」**。`event_bus_manager` 已存在但无人 publish/subscribe。把「实例状态迁移 / 节点完成 / 违规 / 降级」统一为领域事件后，审计落盘、计量、SSE、Webhook、第三方集成全部变成订阅方——一次改造同时满足 F8 与治理可信（8 人日，**全项目单点收益最高**）。
2. **LangGraph 适配：由「删」改「留」**。v1 建议删除以减负；v2 认为应补齐并作为**第二运行时**——「同一份 YAML 在内置引擎与 LangGraph 上跑出等价结果」是「契约可移植」的唯一硬证明，也是对 Dify 的实质差异。代价是维护两套执行语义，故只保证「子集等价」（顺序/条件/单层循环），并在文档中明确等价边界（6 人日）。
3. **依赖注入容器**：`application_factory.py` 300+ 行靠模块级单例装配。手工轻量容器，按「配置选择实现」启动期装配一次（5 人日）。

### 6.3 代码质量与可维护性

| 项 | 建议 | 成本 |
| --- | --- | --- |
| `NodeConfigurationPanel.tsx` 3710 行 | 按节点类型拆 `panels/<node_type>/index.tsx`，共享 `Field` 基元，对外 props 不变 | 6 人日 |
| 15 个 API 客户端 | 抽 `api/httpClient.ts`（token、租户头、超时、重试、错误映射），客户端只留端点定义 | 4 人日 |
| 3 份异常类 | 统一 `ApiError`，按 `code` 分层 | 1 人日 |
| 无 CI | 见 F5；先「不新增失败」门禁，再清零基线 | （已计） |
| 文档漂移 | README 重写为能力地图；`phase4_ecosystem_summary.md` 对齐 `settings.py`；新增 `deploy.md` / `config.md` / `api-reference.md` | 3 人日 |

### 6.4 性能（按路线取舍）

1. **R2 必需**：`data_transform` 全内存 → 分块流式（F16）；否则 ETL 场景不成立。
2. **R1 必需**：执行状态全落库 + 多副本（F9）；当前单进程串行是吞吐天花板。
3. **可延后**：前端首屏（18 面板全量打包）→ `React.lazy` + 路由，首屏 JS 降 40–60%（2 人日，需先补路由）；`localStorage` 全量覆盖写 → 防抖 300ms + 只写 nodes/edges（2 人日）。
4. **可延后**：LLM 单次 `httpx` 无流式无重试 → 流式 + 指数退避 + 连接池单例（4 人日）。
5. **降级为技术债**：向量检索暴力 O(N·D) + 伪向量 → 换 pgvector **只为不再撒谎**，不作为 RAG 产品方向投入。

### 6.5 可观测性

- `run_log` 是现成优势但缺 trace 串联。OTel 贯穿「API → 调度 → 节点 → LLM」并导出 OTLP（6 人日）——**在 R1 场景这是加分项而非必需**（客户已有自己的 APM），排在 R1 交付之后。
- 指标 Prometheus 化（3 人日）同理，R1 试点客户提出后再做。

## 9. 方向五：差异化与「不做什么」

完整分析见 `docs/differentiation-strategy-2026-11.md`（竞品基线、四条路线评分、对客话术、风险矩阵）。此处只放结论：

**三句话定位**

1. **可嵌入**——Dify 许可证禁止多租户 OEM 与去 logo，ISV 是真空；我们做「能被装进别人产品里的编排内核」。
2. **可移植**——YAML 是契约而非导出物：可校验、可 diff、可进 CI、可编译到第二运行时。客户不被锁定。
3. **可审计**——治理是架构内建而非商业版补丁：审计、计量、配额、降级同源事件流。

**不做什么（比做什么更重要）**

模板市场、插件市场、模型聚合面板、Prompt IDE、零代码 C 端 Bot、自研向量库、通用 RAG 问答、NL Copilot。

> 判据：**一旦开始说「我们也支持 RAG / 也支持并行」，就会被拉回 Dify 擅长的战场**。所有对外表述必须停在「位置差异」，不停在「能力比较」。
