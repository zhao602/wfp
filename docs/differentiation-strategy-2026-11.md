# 差异化竞争路线分析（对标 Dify / n8n / LangGraph / Temporal）

> 基线：2026-11-17。竞品事实取自各家公开文档与 2026 年发布说明；本项目事实取自代码与
> `docs/architecture-review-2026-11.md` 的能力矩阵。
>
> 一句话结论：**不要在「可视化搭 AI 应用」这条主赛道上和 Dify 拼功能密度**——它的
> 节点数、插件数、模板数、模型数都已经是数量级优势。可赢的位置只有三个结构性空位：
> **可嵌入（OEM/白标）、声明式契约（YAML 即接口）、执行可审计（治理内建）**。

---

## 1. 竞品现状基线（2026-11）

| 产品 | 当前形态 | 真正的护城河 | 结构性软肋（可攻击面） |
|---|---|---|---|
| **Dify** | 1.19.0（2026-11-04），15.7 万 star，官方称 140 万台机器部署、280+ 企业客户；1.9.0 起改为队列化图执行引擎 | 产品完整度：画布 + Knowledge Pipeline + Agent + 插件市场 + 模板市场 + MCP 双向；**心智占领**（"AI 应用开发平台"= Dify） | ① 许可证是 Apache 2.0 **加附加条款**：多租户对外服务、去除 logo 均需书面授权——**ISV/OEM 场景是法律禁区**；② 重心在 LLM 应用，数据工程能力近乎为零；③ 编排语义是产品内部的 JSON DSL，非可校验规范；④ 企业治理能力（SSO/RBAC/审计/SOC2）在**商业版**，社区版没有 |
| **n8n** | 集成类工作流自动化，fair-code（Sustainable Use License） | 400+ 连接器、触发器生态、运维工程师心智 | Agent/RAG 抽象弱，只能当"工具调用层"；不适合作为 AI 应用底座 |
| **LangGraph** | 代码级图编排框架 + LangGraph Platform | durable execution、状态机语义严谨、LangSmith 可观测 | 无画布、无治理、无多租户；业务方无法参与，交付依赖工程团队 |
| **Temporal** | 通用 durable execution 引擎 | 事件溯源、无限重试、确定性重放，工业级可靠 | 无 AI 抽象、无图编排 UI，业务人员不可用 |
| **Coze / FastGPT / RAGFlow** | 零代码 Bot / RAG 专项 | 上手速度、渠道发布、RAG 精度 | 私有化与深度定制弱，复杂流程顶到天花板 |

**由此得出的三个空位**：

1. **多租户 OEM 空位**——Dify 的许可证明确挡掉了「把编排能力嵌进自己产品再卖给客户」这条路。所有做行业 SaaS 的厂商都被迫自研或找替代品。
2. **数据 × AI 混合 DAG 空位**——Airflow/Dagster 不懂 LLM 语义，Dify 不懂 ETL。真正"批处理 + 推理 + 人工审核"混合的长流程没人做好。
3. **"编排内核"空位**——LangGraph 是库不是产品，Temporal 是引擎不懂 AI，Dify 是产品不能拆。**可独立部署、可被嵌入、可被审计的执行内核**目前没有强势玩家。

## 2. 本项目的真实底牌与真实负债

### 能打的（已验证，非 PPT）

| 资产 | 证据 | 竞争含义 |
|---|---|---|
| **YAML spec + 三层校验链** | `YamlWorkflowParser`（语法→版本→五要素→pydantic 判别联合）→ `GraphTopologyValidator` → `NodeConfigurationValidator` → `GraphCompiler`；`docs/yaml-spec.md` 有正式规范 | Dify 的 DSL 是**导出物**，本项目的是**契约**。这是唯一能对开发者讲清楚的差异点 |
| **12 套可运行范例 + 注册表** | `examples/` 12 个定义全部通过解析+拓扑+编译；`GET /api/v1/examples` 12 条 available | 可验证的"规范即文档"，竞品靠市场里的用户投稿 |
| **14 类节点 / 21 个数据变换算子** | `domain/models/enums.py`；`engine/nodes/data_transform_ops/`（cleaning/structure/dev/ai 四类处理器 + 正则安全 + 脱敏） | 数据工程纵深是 Dify 的空白区 |
| **治理链架构** | `governance/`：tenant / rbac / audit / metering / cache / event_bus / degraded_mode / interceptors 全部有骨架与单测 | 治理是**一等公民**而非商业版补丁。注意：**目前是接线未完成状态**（见负债） |
| **检查点 / 回滚 / 重放 Protocol** | `persistence/abstractions` + `rollback_replay_router` | 有 durable execution 的接口形状（当前路由为桩） |
| **单游标确定性调度** | `engine/scheduler.py`，语义明确、无隐式并发 | 可解释、可重放——比"神秘并发"更适合受监管场景 |
| 测试厚度 | 后端 pytest 2797 例 exit 0；前端 115 文件 / 916 例 | 对 to B 客户是可信度资产（前提是接上 CI） |

### 不能打的（必须诚实）

- **产品完整度**：节点/插件/模板/模型数量都差 1–2 个数量级，正面拼功能密度必输。
- **上手体验**：Dify 一条 docker compose 起全栈；本项目无 Dockerfile、无 CI、无部署文档。
- **生态**：插件市场、模板市场、社区，从零开始不可能追上。
- **已交付但没接线的能力**：检查点未传 repo、HITL `suspend` 未消费、回滚路由直返成功、审计查询恒空、RBAC 权限缓存恒空（开启即 403）、MCP 缺 JSON-RPC 信封、向量是暴力检索 + 伪向量。**这些在对外叙事里一个都不能提"已支持"。**

## 3. 四条候选路线

评分：契合度 = 与现有代码资产的复用程度；烈度 = 该赛道现有竞争强度（越高越难）；
护城河 = 建立后可持续性；投入 = 达到"可对外交付"所需人日（粗估）。

| # | 路线 | 一句话 | 契合度 | 烈度 | 护城河 | 投入 | 综合 |
|---|---|---|---|---|---|---|---|
| **R1** | **可嵌入编排内核（OEM / 白标）** | 把 `wfp` 引擎做成可独立部署的权威执行服务，卖给行业 SaaS / 集成商嵌进自己产品 | ★★★★★ | ★☆☆☆☆ | ★★★★☆ | 35–45 人日 | **9.0** |
| **R2** | **Agentic 数据管道** | 以 21 个数据变换算子 + 数据源连接器为楔子，做"ETL + 推理 + 人工审核"混合 DAG | ★★★★☆ | ★★☆☆☆ | ★★★☆☆ | 45–60 人日 | **7.5** |
| **R3** | **受监管行业私有化底座** | 面向金融/政务/医疗，用"可审计、可回放、可降级、可配额"打 Dify 商业版 | ★★★☆☆ | ★★★★☆ | ★★★★☆ | 60–80 人日 | **6.5** |
| **R4** | **工作流即代码（GitOps）** | CLI + PR 校验 + 契约测试 + diff，做"编排领域的 Terraform" | ★★★★☆ | ★★★☆☆ | ★★★☆☆ | 20–25 人日 | **7.0** |

### R1 可嵌入编排内核 —— 推荐主线

**为什么能赢**：Dify 许可证挡住了 OEM（多租户对外服务需书面授权），LangGraph 是库需要客户自己写工程，
Temporal 不懂 AI。这个位置**目前是真空，且真空是法律/定位造成的，不是技术造成的**——短期不会被填。

**形态**：`wfp-engine` 单二进制/单容器，暴露 gRPC + HTTP；无内置 UI（或 UI 可裁剪）；
客户产品通过 SDK 提交工作流定义、触发执行、订阅事件流。YAML spec 作为**客户与引擎之间的稳定接口**。

**必须补的**：多租户落库（tenant_id 行级隔离 + RLS）、API Key/租户配额、事件出口（Webhook/SSE）、
无状态水平扩展（执行状态全落库）、OEM 构建（去 logo、可主题化）、版本兼容承诺（spec 1.x 不破坏）。

**验收**：一个外部 Demo——用 100 行代码把引擎嵌进一个假想的"合同审查 SaaS"，跑通 3 个租户、配额限制、审计导出。

### R2 Agentic 数据管道 —— 推荐楔子（场景侧）

**为什么能赢**：客户不会为了"又一个 Dify"换平台，但会为了"我的 ETL 里那 6 个 Python 脚本能换成
可审计的 DAG，并且中间能插 LLM 和人工审核"而换。这是 Dify 结构上不做的场景。

**形态**：`data_engineering` 范例扩成产品级模板库（清洗→校验→脱敏→LLM 抽取→人工复核→入库），
主打"带 AI 的批处理"，与 Airflow 并存而非替代（可作为 Airflow 的一个 Operator）。

**必须补**：真正的扇出/汇聚（当前只取首条出边）、调度触发（Cron）、失败重试与断点续跑、
大批量流式处理（当前全内存）。

### R3 受监管行业底座 —— 不做主线，做 R1/R2 的信任凭证

正面打 Dify Enterprise 需要 SOC2 / 等保 / 行业案例，这是销售与合规投入，不是代码投入，
对本项目当前阶段性价比最低。但**把"可审计、可回放、可降级"做成 R1 的卖点**是免费的。

### R4 工作流即代码 —— 推荐入口（开发者侧）

**为什么值得做**：投入最小（20 人日）、复用最充分（解析器/校验器/编译器都已存在）、
获客最精准（开发者会 star、会提 issue、会写博客）。它是 R1 的漏斗顶部。

**形态**：`wfp` CLI：`wfp validate`（CI 里跑）、`wfp diff`（两个版本语义差异）、
`wfp graph`（输出 mermaid）、`wfp run --local`（本地起引擎跑一遍）、`wfp fmt`。
外加 GitHub Action：PR 里贴出"节点/边变更 + 校验结果"。

## 4. 推荐组合：R1 主 + R4 入口 + R2 楔子

```
开发者 ──> R4 CLI/GitOps ──> 试用引擎 ──> R2 数据管道场景（第一个真实用途）
                                              │
                                              ▼
                                     R1 嵌入到客户产品（商业变现）
```

**叙事一句话**：
> Dify 帮你把 AI 应用**搭出来**；我们帮你把编排能力**装进你自己的产品里**——
> 声明式 YAML 契约、可审计执行、可白标嵌入，许可证不限制你多租户商业化。

### 明确不做（比做什么更重要）

| 不做 | 原因 |
|---|---|
| 模板市场 / 插件市场 | 网络效应已被 Dify 锁定，冷启动不可能 |
| 模型聚合与管理面板 | 商品化能力，做了不加分 |
| Prompt IDE / 提示词调试器 | 同上，且 Dify 已做到极致 |
| 零代码 C 端 Bot | Coze 的地盘，且与"可嵌入内核"定位冲突 |
| 自研向量数据库 | 直接用 pgvector；当前暴力检索是负债不是特色 |
| 通用 RAG 问答产品 | FastGPT/RAGFlow/Dify 三方混战，无差异点 |

## 5. 落地节奏（与架构评审的 90 天路线合并）

| 阶段 | 动作 | 产出 | 验收 |
|---|---|---|---|
| **W1–2 止血** | CI（pytest+vitest+ruff+tsc）、Dockerfile + compose、JWT+RBAC 落库、默认密钥强校验 | 可 `docker compose up` 跑起来的可信版本 | 陌生人 10 分钟内起全栈 |
| **W3–4 立契约** | `wfp` CLI 的 `validate` / `graph` / `diff`；GitHub Action；spec 1.x 兼容承诺文档 | 开发者可把 YAML 纳入 Git 流程 | 12 套范例进 CI 校验，PR 有 diff 报告 |
| **W5–7 补执行** | 检查点接线、`max_steps` 预算、HITL 挂起/恢复、Cron 触发、审计落盘 | 长流程可中断可恢复可追责 | 人工审核节点端到端 demo |
| **W8–10 打楔子** | 并行扇出/汇聚、`data_engineering` 模板产品化、流式处理 | 数据管道场景可交付 | 10 万行数据跑通不 OOM |
| **W11–13 做嵌入** | 多租户 RLS、租户配额、事件出口、SDK、OEM 构建开关 | 可被第三方嵌入 | 外部 Demo SaaS 集成成功 |

**6 个月目标（可量化的差异化证据）**：
1. `wfp validate` 被至少 3 个外部仓库用在 CI 里；
2. 至少 1 个真实 ISV 把引擎嵌进其产品（哪怕免费试点）；
3. 用同一份 YAML 在两种运行时（内置引擎 + 导出到 LangGraph）跑出等价结果——这是"契约可移植"的硬证明，也是 Dify 做不到的。

## 6. 对客户/投资人怎么讲（正面对比话术）

| 维度 | Dify 1.19 | 本项目 | 客户该选谁 |
|---|---|---|---|
| 上手速度 | 一条 compose，5 分钟出 Bot | 需读 spec，30 分钟 | 要快 → Dify |
| 节点与插件 | 数百插件、数十节点 | 14 类节点、无市场 | 要全 → Dify |
| RAG 精度 | Knowledge Pipeline + 混合检索 + rerank | 向量检索为占位实现 | 要 RAG → Dify |
| **许可证与 OEM** | 多租户对外服务需授权，不可去 logo | 可自由嵌入与白标 | **要做产品 → 我们** |
| **定义的可移植性** | JSON DSL，无公开规范 | YAML spec + 三层校验 + 可编译到其他运行时 | **要防锁定 → 我们** |
| **数据工程能力** | 几乎为零 | 21 个算子 + 数据源连接器 | **要跑批 → 我们** |
| **执行可审计** | 商业版审计日志 | 治理拦截器链（审计/计量/配额/降级） | **要合规留痕 → 我们** |
| 生产可靠性 | 队列化引擎，规模验证过 | 单游标，检查点待接线 | 要高并发 → Dify |

**诚实结论**：现在是 0.3 版本对 9.0 版本。差异化不是"我们现在更强"，而是
**"我们站在一个它不能站的位置上，并且这个位置有真实需求"**。所有叙事都必须建立在这个前提上，
一旦开始吹"我们也支持 RAG/也支持并行"，就会立刻被拉回它擅长的战场。

## 7. 风险与反脆弱

| 风险 | 概率 | 应对 |
|---|---|---|
| Dify 修改许可证放开 OEM | 低（其商业模式依赖企业版） | 提前积累"可移植契约"叙事，这一条它放不开 |
| 客户其实只想要开箱即用，不想要内核 | 中高 | 用 R2 场景楔子先建立"能干活"的信任，再谈嵌入 |
| 摊子过大再次"半接线" | 高 | 每个阶段只允许一个对外承诺能力，其余标记 experimental |
| 单人/小团队维护不动 5.7 万行 + 5.5 万行 | 高 | 冻结新增面板 6 个月；前端拆到 3 个包；后端按包设 owner |
| 大厂（阿里/腾讯/字节）推出同类内核 | 中 | 它们做云服务不做私有化嵌入式；护城河在"可离线、可白标" |

## 8. 路线落地进度（2026-11-22 实测）

> 本章为「位置」而非「策略」：策略见 §3–§5 不变，此处只回答四条路线各走到哪一步。数据取自当日代码与测试记录（pytest 3431 collected = 3428 passed + 3 skipped，exit 0）。

### 8.1 四条路线的能力进度

| 路线 | 2026-11-20 | 2026-11-22 | 证据（可复核） |
|---|---|---|---|
| **R1 可嵌入内核** | ≈40%（无 SDK / 无隔离 / 无配额 / 无白标） | **≈85%（能力面闭环）** | `sdk/wfp_sdk/` 9 方法 + `sdk/demo` 端到端 `DEMO PASS`；`v1_7_enable_rls.sql` 24 条策略 + 58 跨租户负向用例；配额 429 + 对账零差异（B4）；Webhook/SSE 0 丢失 6/6、p95 < 2s（B3）；`oem/dist/acmeflow` 双品牌 16 项断言（B5） |
| **R4 工作流即代码** | ≈95% | **≈95%（未推进）** | `wfp validate/diff/graph/run` 四子命令 + `.github/workflows/wfp-check.yml` |
| **R2 Agentic 数据管道** | ≈5%（仅 Cron） | **≈35%** | 并行扇出落地：`WAIT_ALL/ANY/N_OF_M` + 前沿恢复 + 23 新用例（B6）；仍缺流式分块、批量管道模板、吞吐基线 |
| **R3 受监管背书** | 0 | **0（未启动）** | 无合规报告、无第三方审计、无行业案例 |

### 8.2 能力到位 ≠ 位置到位：四道未开的门

| 门 | 现状 | 阻塞后果 | 成本 |
|---|---|---|---|
| **法律**：LICENSE | 全仓无 `LICENSE` 文件，`pyproject.toml` 无 `license` 字段 | 默认「保留所有权利」，任何人不能合法嵌入或白标——R1 全部商业前提落空 | 0.5 人日（需决策：Apache-2.0 / BSL / 双许可） |
| **分发**：公开可达 | 无 `git remote`、无版本提交；SDK 仅本地 wheel，未上 PyPI；无 TS/Java 客户端 | 外部拿不到、装不上，"可嵌入"只是内部事实 | 3–4 人日 |
| **证明**：可复现基准 | 无第三方可跑的性能基线；双运行时等价仅内部 13 例；README 仍写「单游标调度 / 企业级平台」旧定位 | 尽调时无法自证"并发/白标/契约可移植" | 4–5 人日 |
| **采用**：外部试点 | 0 个外部 ISV、0 个试点客户、无托管 Demo | 无法回答「谁在用」，差异化停留在自证 | 不可由工程单独解决 |

### 8.3 结论

- **坐标已右移**：从「纸面上可嵌入」变成「跑起来可嵌入」，能力侧与 LangGraph 同侧、与 Dify 反向。
- **标记仍是虚线**：无 LICENSE + 无公开仓库 + 无分发，意味着这份能力在法律与分发意义上尚不存在。
- **B7 收割批未收口**（T5–T10 未勾）：`tenant_id` 传播统一、订阅注册表落盘（当前重启丢失订阅）、`docs/spec-versioning.md`（1.x 只增不删承诺）——这三项恰是对外承诺的一部分，未收口即对外谈交付会翻车。
- **下一步不是加功能**：把 L1.5 推到 L2（外人 10 分钟内能装、能跑、能对比）约 8–10 人日，收益高于再加一个面板一个数量级。
