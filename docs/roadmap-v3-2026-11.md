# 后续拓展与完善方向（v3 · 2026-11-22）

> **本文定位**：接替 `docs/project-status-and-roadmap-2026-11.md` §7 的批次计划。B0–B6 已于 2026-11-21～22 全部收口（SDK、多租户 RLS、事件出口、计量配额、OEM 白标、并行扇出），原计划已执行完毕，本文回答「下一步往哪走」。
>
> **不重复的内容**：能力事实与代码位置见 `docs/architecture-review-2026-11.md`；竞品论证与路线选择见 `docs/differentiation-strategy-2026-11.md`（§8 为本次进度基线）。
>
> **结构**：第一部分为非代码推进（置顶，因为它决定代码投入是否有意义）；第二部分为代码实现方案，按功能、架构、性能、体验、测试、安全六维展开；第三部分分层排期；第四部分给出优先级筛子与裁剪清单；附录为假设与度量基线。

## 一页结论

1. **卡点不在代码**。许可证缺位、仓库无公开可达路径、SDK 未分发、无外部试点——四件事合计不到 10 人日，却决定全部 R1 能力的对外意义。
2. **最该先修的代码问题是「执行进程内」**：`asyncio.create_task` 执行、无 worker、无接管，多副本与滚动升级即丢任务。这直接否掉「可嵌入」的部署前提。
3. **测试的缺口是跨层而非单层**：123 个前端测试文件、3431 个后端用例，但零 e2e。B0 那类「表名对不上、装配即失败」的问题，只有 e2e/冒烟能提前发现。
4. **性能与可观测仍无基线**：`/metrics` 是 JSON，无 OTel/Prometheus，无吞吐数字。没有基线，后面所有「优化」都无法验收。
5. **能力宣称必须与实现同步降级**：SSO（`governance/sso/` 共 329 行，未见断言验签）、LangGraph 的 resume/rollback/replay（明确抛错）都应标 experimental 或从对外能力表移除，避免「假支持」。

# 第一部分 非代码推进（置顶）

## 1.1 为什么先做这些

能力已经做到「可演示」，但对外仍是「不可获取、不可授权、不可验证」。这三件事都不写代码，却决定第二部分每一项投入能否转化为客户。**建议在动任何新功能前，先花 2 周把这一部分做完。**

# 第四部分 优先级依据与裁剪

## 4.1 三条筛子（按序判定）

1. **是否服务对外承诺**：不服务「可嵌入 / 可审计 / 可移植」三句话的，一律 P2 以下。许可证、分发、基准、e2e、执行无状态化因此排在前面。
2. **是否是「假支持」风险**：能力已暴露但实现不完整（SSO、双运行时子集、并行 UI）优先于新增能力——被尽调发现一次，信任成本远高于补功能。
3. **是否有判定依据**：没有基线（P1）、没有 e2e（T1）、没有版本（F3）时，相关优化不立项，避免「优化了但说不清」。

## 4.2 明确不做（本轮）

| 事项 | 理由 |
|---|---|
| 模板市场 / 插件市场 | 网络效应已被 Dify 锁定，投入产出比最低 |
| 通用 RAG 问答产品化 | 向量库仅作节点能力，与主线无关 |
| 多模型聚合面板 / Prompt IDE | Dify 主场，正面无胜算 |
| 表单化编排 / NL Copilot 深化 | 不服务嵌入场景 |
| 评估闭环 / Agent 发现产品化 | 无试点客户时无法定义「好」 |
| 前端框架迁移（react-router 等） | 自研路由已够用，迁移无对外收益 |
| C 端 Bot / 多租户 SaaS 自营 | 与「被嵌入」定位冲突 |
